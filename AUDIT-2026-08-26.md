### 1.3 Signal path: ingestion → detection → pricing → risk → execution

There are **two** entry points into `_evaluate_lock_in`, and they have very different latency:

**(A) Event-driven (the fast path).**
```

  → _process(obs)                 dedupe on observed_at_utc; plausibility; dewpoint check
  → _update_validated_max()       glitch guard (kinematic rise / 5-min confirm / neighbour)
  → db.upsert_tmax()              writes daily_tmax  (IN PLACE — no history)
  → engine.on_new_high(icao, climate_date, tmax_f)
      → for each market on that station with matching event_date:
          _evaluate_lock_in(market, climate_date, tmax_f)
```

**(B) Periodic (the slow path).** `ArbitrageEngine.run` → `evaluate_all()` →
`evaluate_market()` for all 84 markets concurrently, every **120 s**; reads `daily_tmax`
from the DB and calls `_evaluate_lock_in` plus `_evaluate_model_edge`.

**Inside `_evaluate_lock_in`** ([arb_engine.py:491](weather_arb/arb_engine.py#L491)):

```
market.deterministic_lock_in(tmax_f)  → (side, action) | None      ← THE DETECTION
  ↓ (per-ticker asyncio.Lock)
_is_tradeable(ticker)                 ← 60 s-cached GET /markets/{ticker}, fail-open
db idempotency check                  ← one lock-in order per ticker per climate day
_get_book(ticker)                     ← cached WS book if fresh (never, no WS) else GET orderbook
best = book.best_yes_ask | best_no_ask
desired = book.buyable_{yes,no}_size(ceiling=98)      ← DEPTH-AWARE: sums ALL levels ≤ 98¢
if best is None or best.price_cents >= 98 or desired <= 0:  return   ← THE PRICE GATE
LimitOrderRequest(price=min(best.price_cents, 98), count=desired, strategy=LOCK_IN)
  ↓
_submit → RiskManager.size_order      ← caps, live-clearance gate, (Kelly is a no-op for S1)
  ↓
db.upsert_open_order(PENDING)         ← journalled BEFORE transmit
  ↓
client.place_limit_order()            ← DRY-RUN: logs, returns RESTING with filled_count=0
  ↓
db.set_order_status(...)              ← filled_count==0 ⇒ _record_fill never runs ⇒ trades stays empty
  ↓
_push_lock_in()                       ← ntfy via asyncio.to_thread
```

**Pricing note that matters for §5:** the live engine never buys at the headline ask. It
computes `desired = buyable_no_size(98)` — the sum of *every* ask level at or below 98¢ — and
sends a marketable limit at that ceiling. A book of `14¢ ×1, 18¢ ×12, 98¢ ×200` yields an
order for **213 contracts at ≈87.6¢ VWAP**, not 100 at 14¢.

### 2.2 Timestamps, normalisation, dedupe

- **Observation timestamp** = `obsTime` (epoch seconds) from AWC → `MetarObservation.observed_at_utc`.
  This is the METAR's own valid time (e.g. `2026-08-26T02:54:00Z`), not receipt time.
- **Temperature** arrives as °C and is converted in `MetarObservation.temp_f`. AWC's `temp`
  carries the tenths-of-°C `T`-group when present, so stored °F values are things like
  `84.02`, `93.02`, `71.96` — i.e. **within ±0.08 °F of an integer for 93.2 % of all 9,056
  rows** (measured). This fact is the direct cause of the false-positive mode in §3.5.
- **Dedupe:** `_process` skips any observation whose `observed_at_utc <= track.last_obs_time`.
  Per (icao, climate_date) track.
- **Climate day:** fixed Local-Standard-Time offset, **no DST** (`timeutils.climate_date_str`),
  matching Kalshi's settlement window. KNYC −5, KMDW/KAUS −6, KDEN −7, KLAX −8, KMIA/KPHL −5.
- **Missing observations:** no interpolation. A gap simply means `daily_tmax` does not advance.
  Rejected observations are still written to `station_logs` with `accepted=0`.
- **Authoritativeness:** `market_discovery` calls `verify_mappings.classify_rules` on Kalshi's
  `rules_primary` and blocks a series whose CLI product code drifts from `EXPECTED_AUTHORITY`.
  This ran 24 times with `could not confirm settlement station from rules (continuing to trade)`
  — i.e. **it fails open**, it does not halt.

### 2.4 t1 / t2 / delta — **the answer, measured**

The question has three distinct timestamps, and conflating them is where the project's
documentation has gone wrong before. Definitions used here:

| symbol | meaning |
|---|---|
| `t0` | the physical instant the air temperature actually crossed the bucket boundary |
| `t1_current` | the earliest timestamp at which **the current system's wired data sources** could know the outcome is deterministic |
| `t2_current` | the timestamp at which the system **actually** learns it |

**`t1_current` = the METAR's `observed_at_utc`.** With only hourly METAR wired in, there is no
earlier information in the system. It is a *report* timestamp, ~:51–:54 past the hour.

**`t2_current` = `t1_current` + ingest latency + detection latency.**

- Ingest latency at the 564 reconstructed detections: **median 200 s, p90 300 s, max 1,599 s.**
- Detection latency after ingest: `on_new_high` fires **synchronously inside the poll cycle**,
  so it is ~0 for the fast path. The periodic path adds up to 120 s, but it is never the first
  to see a new max.

**`delta = t2_current − t1_current` ≈ 200 s median (3.3 min), 300 s p90.**
This is genuinely small and is **not** where the money is.

**The economically relevant gap is `t0 → t2`, and it is ~50× larger.** The hourly METAR is an
instantaneous reading published on the hour; the temperature crossed the boundary somewhere in
the preceding hour. Independent measurement in §15.3 puts the median at **53 minutes**
(n = 412, from a feed the system does not currently use). So:

```
t0  ──────── ~53 min (median) ────────►  t1_current  ── ~3.3 min ──►  t2_current
    ▲ outcome is physically certain      ▲ METAR reports it          ▲ we know it
    └──────────────── the entire exploitable window ────────────────┘
```

**The 3.3-minute engineering latency is already good. The ~53-minute observation gap is the
whole opportunity, and closing it is a data-acquisition problem.**

### 2.5 The glitch guard is load-bearing for *safety*, not just accuracy

`metar_ingest._accept_step` applies, in order: (1) `plausible_rise()` — a kinematic check
allowing `8 °F/h × elapsed + 1 °F`, capped at 15 °F, flat 2 °F for sub-minute updates, cooling
never rate-limited; (2) 5-minute re-confirmation; (3) neighbour-station corroboration. It
measures from the last **trusted** reading, not the last raw one.

Audit finding: replaying the lock-in rule over **raw** `station_logs` produces a
**138.2 °F** reading at KDEN on 2026-08-16 that fires two wrong lock-ins. The guard rejects it
(`daily_tmax` for that day is 80.96). **So the guard is currently the only thing standing
between a sensor spike and a wrong "riskless" trade at up to 98¢.** There is no independent
sanity check downstream of it in `deterministic_lock_in`.

Log evidence of the guard working: `unconfirmed temperature spike held pending` × 602;
`spike corroborated by neighbor station` × 4.

## 3. DETERMINISTIC LOCK-IN LOGIC

### 3.1 Implementation

**File:** [weather_arb/models.py:373](weather_arb/models.py#L373)
**Method:** `WeatherMarket.deterministic_lock_in(self, observed_tmax_f: float)`
**Input:** one float — the running daily max in °F, read from `daily_tmax`.
**Output:** `Optional[tuple[Side, Action]]` — `(Side.NO, Action.BUY)`, `(Side.YES, Action.BUY)`, or `None`.

```python
lo, hi = self.floor_f, self.cap_f
if hi is not None and observed_tmax_f > hi:                 # certain NO
    return (Side.NO, Action.BUY)
if hi is None and lo is not None:                           # tail-high only
    hit = observed_tmax_f > lo if self.kind == STRIKE_GREATER else observed_tmax_f >= lo
    if hit:
        return (Side.YES, Action.BUY)
return None
```

There are **no thresholds, no tolerances, and no margin requirement.** The comparison is a bare
float `>` against an integer strike.

### 3.2 Downstream thresholds (all outside the rule itself)

| Knob | Value | Where |
|---|---|---|
| `lock_in_price_ceiling_cents` | **98** | `config.py:62`; refuses any ask ≥ 98¢ |
| `max_fraction_per_market` | **0.05** | `WA_MAX_FRACTION_PER_MARKET`; $500 on $10k equity |
| `max_fraction_per_group` | **0.0** (disabled) | |
| `kelly_fraction` | **0.0**, and **a no-op for Strategy 1 regardless** — `risk_manager.py:186` requires `strategy is MODEL_EDGE and win_prob is not None`; lock-ins carry neither | |
| order size | `buyable_{yes,no}_size(98)` — the full sweepable depth ≤ 98¢, then capped by risk | |

### 3.3 The stated validity argument, and where it breaks

The argument is: the daily max is monotone non-decreasing, so once the running max exceeds a
bucket's cap the bucket can never settle YES. **That is valid for the running max.** It is
*not* valid as applied, because two different quantities are being conflated:

- `observed_tmax_f` — a **float** °F derived from a tenths-of-°C METAR reading (e.g. `84.02`).
- the settlement value — a **whole-degree-°F integer** from the NWS CLI, produced by rounding
  the continuous record.

`84.02 > 84` is true, so the rule declares the `{83, 84}` bucket a certain NO. But if the day's
true maximum was, say, 84.3 °F, the CLI reports **84**, and that bucket settles **YES**.

The project's stated defence (`CLAUDE.md`: *"our METAR values sit within ±0.08 of an integer …
so `run > cap` can never fire inside the ambiguous `(cap, cap+0.5)` band"*) **inverts the
logic.** Sitting within ±0.08 of an integer is precisely what places a value like `84.02`
*inside* the ambiguous band `(84, 84.5)`. The observation is correct; the inference from it is
backwards.

### 3.4 Why the backtest reported zero wrong calls

[backtest.py:245-268](weather_arb/backtest.py#L245). The control flow is:

```python
if entry is None:      detected["no_quote"] += 1;   continue     # never graded
if entry >= _CEILING:  detected["priced_out"] += 1; continue     # never graded  ← 420 of 421
detected["tradeable"] += 1
won = (side == result)          # ← the ONLY place a call is checked against settlement
rows.append({... "matched_result": won ...})
```

`_summarize` computes `settlement_mismatches` from `rows`, and `rows` contains **only the
tradeable detections**. In the 30-day run that is **1 row**. `_render` then prints
`correct / wrong calls : {wins} / {mismatches}` — which for that run reads **`1 / 0`**, not
`421 / 0`.

**Therefore: "421 detections, 0 wrong calls" is a documentation error twice over.** The code
never graded 421 detections, and the number printed on that line is the tradeable count, not
the detection count. The 420 priced-out detections were counted, tabulated, and **never
compared to settlement at all.** This claim is listed under "SOLID — mechanically verified,
reproducible, locked by tests" in `HANDOFF.md`. It is none of those things.

**Economic magnitude.** A wrong certain-NO buys NO at up to 98¢ and settles at 0. At the
configured `max_fraction_per_market = 0.05` on $10k equity, that is up to **−$500 per event**.
The corrected Strategy-1 backtest found **1 tradeable opportunity in 30 days worth +$3.73**.
The strategy's own measured upside is ~$45/year; a single false positive that clears the price
gate wipes out a decade of it.

**Important uncertainty, stated plainly:** all 16 sub-0.1 °F errors are at markets that were
almost certainly priced at 100¢ (the price gate would have refused them), so **none of them
would have traded.** This audit cannot verify that, because no book data exists for those
moments (§7). The correct reading is: *the detection rule is unsound, and the only thing that
has prevented a loss is a price gate whose protection has never been measured.* Relying on
"the market is always at 100¢" as a safety property is exactly the assumption the whole
latency thesis says is false 28 % of the time.

### 3.6 The `R >= 0` safety proof is false

`HANDOFF.md`: *"`R = CLI − hourly-METAR max`: mean +0.81 °F, RMS 1.08, range [0, 3], **never
negative** (n=245). `R >= 0` is what makes Strategy 1 safe."*

Re-derived from local data. For each of the 245 settled station-days, the YES bucket constrains
the CLI integer `S` to a range; compare against the raw METAR max:

```
S_max <  METAR max   (R DEFINITELY NEGATIVE) :  16   ← 6.5 %
METAR max within the S range (R may be < 0)  :  74
S_min >= METAR max   (R >= 0 guaranteed)     : 155
```

Definitive negatives include `KNYC 2026-08-04` (METAR 84.02, S ∈ [83,84] ⇒ R ≤ −0.02),
`KMIA 2026-07-31` (96.08, S ∈ [95,96] ⇒ R ≤ −0.08), `KLAX 2026-08-14` (78.08, S ∈ [77,78]).

The original result was almost certainly produced by rounding the METAR max to an integer
before differencing, which maps `84.02 → 84` and turns `R = −0.02` into `R = 0`. The histogram
`{0: 86, 1: 121, 2: 36, 3: 2}` being all-integer is consistent with exactly that.

**Consequence:** the mathematical justification for calling Strategy 1 riskless does not hold.
The residual is *usually* positive and *large* (mean ≈ +0.8 °F), which is why 546/564 calls are
right — but it is not one-sided, and the rule has no margin to absorb the exceptions.

### 3.7 Failure modes, enumerated

**False positives (system believes an outcome is locked when it is not):**
1. **Sub-degree boundary straddle — CONFIRMED, 2.8 % of detections.** §3.5.
2. **Sensor spike passing the guard.** The 138.2 °F KDEN reading was caught; nothing guarantees
   the next one is. There is no post-guard sanity check inside `deterministic_lock_in`.
3. **Wrong climate-day attribution.** Fixed-LST offsets are hardcoded; a Kalshi settlement-window
   change would silently misattribute observations. Unmonitored.
4. **Wrong station.** `market_discovery`'s authority check **fails open** (24 occurrences of
   `could not confirm settlement station from rules (continuing to trade)`).
5. **Stale `market_geometry` / strike drift.** `floor_strike`/`cap_strike` come from the API at
   discovery time; a mid-day re-listing is not re-validated.

**False negatives (a genuine lock-in is missed):**
1. **The dominant one, by design:** a tail-high YES needs the *hourly METAR* max to exceed the
   floor, but settlement is the CLI running ~0.8 °F higher. Days where the CLI crosses but the
   METAR does not are never provable. Only **8 of 564** detections were YES-side — the YES
   branch is nearly dead.
2. Observation gaps (`max` ingest latency 15.3 h) mean the max may not advance for hours.
3. `close_time_utc` guard in `evaluate_market` skips markets whose window has closed.

**Order-book structure.** Kalshi expresses both sides as resting *bids*.
`_orderbook_from_kalshi` stores `yes_bids` and `no_bids`; `OrderBook.yes_asks` derives the YES
ask ladder as `100 − no_bid` and `no_asks` as `100 − yes_bid`. This inversion is done in exactly
one place and is reused by `get_l2_sweep_metrics` and `buyable_*_size`.

**Timestamp resolution — a real gap.** `OrderBook.timestamp = timeutils.utc_now()`, i.e. our
*receipt* time. The parser discards any server-side timestamp. **We have no measurement of
Kalshi-side quote age or of our round-trip latency to the exchange.**

## 5. THE 17.4¢ HISTORICAL EDGE — mathematical definition and audit

### 5.1 First finding: it is not reproducible

`git show --stat 36583d1 bd3348e` — the two commits that produced the entire latency-edge
result — modified **`CLAUDE.md` only**. 53 and 39 lines of prose respectively. **No script, no
query, no cached dataset, no test.** `find . -name '*.py' -newermt 2026-08-25` returns only
`models.py`, `arb_engine.py`, `test_v32.py`, `test_v33.py` — all L2-probe work, none of it the
analysis.

**There is no artefact in this repository capable of regenerating the 17.4¢ number, the 247
windows, the 68 discounted windows, the $1,183 estimate, or the liquidity figures.** They exist
solely as prose. This audit cannot verify or refute them; it can only characterise the method
from what the prose describes and from the code that method must have used.

### 5.2 Reconstructed definition, from the prose + `backtest._entry_cents`

The described method: for each detected lock-in, find `t1` (the 1-minute record proves
certainty) and `t2` (the hourly METAR proves it), read the book at each, and take
`discount = 100 − ask(t1)`.

The only price-reading function in the repo is
[`backtest._entry_cents`](weather_arb/backtest.py#L183):

```python
params = {"start_ts": cross_ts - 3600, "end_ts": cross_ts + 6*3600, "period_interval": 60}
for c in candles:
    if c["end_period_ts"] < cross_ts: continue
    if side == "yes":  return round(c["yes_ask"]["close_dollars"] * 100)
    else:              return round((1.0 - c["yes_bid"]["close_dollars"]) * 100)
```

So, precisely:

- **Price used:** the **close of the first 1-minute candle ending at or after the crossing**.
  For a YES lock-in, `yes_ask.close`. For a NO lock-in, `100 − yes_bid.close` (the synthetic NO
  ask). **Not** a midpoint, **not** a trade print, **not** the book.
- **Price timestamp:** the candle's `end_period_ts` — up to 60 s *after* the crossing.
- **Alignment:** weather timestamp is the IEM observation time; market timestamp is a Kalshi
  candle boundary. Both UTC. No adjustment for METAR publication lag on either side.
- **Reported:** 247 windows, 7 stations, 20 days; 68 (28 %) below 98¢, mean discount 17.4¢,
  median ask 100¢; extrapolated $1,183 per 100 contracts over 20 days.

### 5.3 Every reason 17.4¢ is overstated

1. **[SEVERE] It prices top-of-book against an order the engine would never send.** The candle
   gives one price with no size. The live engine sizes with `buyable_no_size(98)` and pays a
   marketable limit, sweeping every level ≤ 98¢. The project's own worked example: `14¢ ×1,
   18¢ ×12, 98¢ ×200` → 213 contracts at **87.6¢ VWAP**, a **12.4¢** edge, not 86¢. The
   direction of the bias is known; the magnitude is not. This alone can plausibly erase most of
   the 17.4¢.
2. **[SEVERE] The candle *close* is a look-ahead artefact.** `_entry_cents` takes the close of
   a bar that ends up to 60 s after the crossing. If the market repriced within that minute, the
   close is *post*-repricing and would understate the edge; if the bar is thin, the close may be
   the only print in it and represent a moment we could not have traded at. Either way the price
   is not "the price at t1". Note the project already found and fixed exactly this class of bug
   once — `period_interval=60` was previously read as seconds, giving hourly bars and a
   **$0.81/trade** optimism on Strategy 2.
3. **[SEVERE] Survivorship at the market level.** `_settled_markets` filters to markets that
   settled with a YES/NO result. Markets voided, halted, or re-listed never enter the sample.
4. **[HIGH] Selection on the detection rule, which is itself unsound.** The 247 windows are
   selected by the same `deterministic_lock_in` shown in §3.5 to be wrong 3.2 % of the time,
   and 9.5 % wrong in the sub-0.1 °F band. If a discounted market is discounted *because it is
   genuinely uncertain* (i.e. we are in the ambiguous band and the market correctly does not
   believe the outcome is settled), the selection is **adversely correlated with correctness**.
   That is the single most dangerous possibility in this whole document and it is untested.
5. **[HIGH] A quote is not liquidity.** A resting ask may be cancelled before an order arrives.
   The candlestick endpoint carries no size at all, so no fill probability can be inferred.
6. **[HIGH] The whole thing is anchored on an unreachable `t1`.** `t1` came from the IEM
   1-minute archive, which (§2.6) is 18–58 h stale and **~38–50 % incomplete**. The lead
   distribution was measured on a series with half its minutes missing.
7. **[MEDIUM] No fees, and no bid-ask asymmetry.** The prose reports the *gross* discount.
   Kalshi's fee near 98¢ is small (`0.07·P·(1−P)` ≈ 0.14¢) but not zero, and at the discounted
   prices that carry the mean it is materially larger (at 80¢: 1.12¢/contract).
8. **[MEDIUM] Mean over a heavily skewed distribution.** Median = 100¢; 56 % of windows have
   zero edge. The 17.4¢ is a conditional mean over the 28 % tail, n = 68 — thin, and it is not
   reported with a dispersion or a per-station breakdown.
9. **[MEDIUM] Measurement-health prior.** The project's own note records that this specific
   analysis produced **three wrong intermediate answers** before landing (out-of-range candle
   query read as "never traded"; `volume`/`open_interest` used instead of
   `volume_fp`/`open_interest_fp`). Two were reported as conclusions before being caught.
10. **[LOW] No market-impact model.** 100 contracts against a book whose top level may hold 1.
11. **[LOW] 20 days, one season, seven stations.** No winter data anywhere in this project.

### 5.4 Was the historical price executable?

**Unknown and unknowable from stored data.** The candlestick endpoint carries no depth. No book
was ever persisted. This is the central unresolved question of the entire project and §12
exists to answer it.

## 6. L2 / EXECUTABILITY

### 6.1 `OrderBook.get_l2_sweep_metrics` — [models.py:180](weather_arb/models.py#L180)

```python
ladder = self.yes_asks if action_side is Side.YES else self.no_asks   # best-first
depth  = sum(lvl.size for lvl in ladder)
filled, cost = 0, 0
for lvl in ladder:
    if filled >= target: break
    take = min(lvl.size, target - filled)
    filled += take; cost += take * lvl.price_cents
return {"top_levels", "vwap_cents", "book_cleared", "fillable_size", "depth_size", "top_ask_cents"}
```

**Endpoint:** none of its own. It is a pure function over an `OrderBook` that came from
`GET /markets/{ticker}/orderbook?depth=32` (or, if credentials existed, the WS feed).

| Question | Answer |
|---|---|
| Displayed liquidity or actual fills? | **Displayed only.** It walks resting size in a snapshot. |
| Depth calculation | Greedy best-first walk to `target_size`; `depth_size` is the whole ladder sum. Correct, and unit-tested (`tests/test_v32.py`, incl. the `14¢ ×1 … 98¢ ×200` → 87.56¢ case). |
| Fees included? | **No.** Pure price arithmetic. |
| Slippage? | **Yes, within the snapshot** — that is exactly what VWAP-vs-top-ask captures. **No** market impact, no adverse selection, no movement between snapshot and arrival. |
| Queue position? | **No.** Irrelevant for a taker, essential if passive placement is ever reconsidered. |
| Stale / cancelled orders? | **No.** A snapshot cannot distinguish a firm quote from one about to be pulled. |
| Can it reconstruct what was executable at each price? | **For the instant of the snapshot, yes — displayed size per level.** For any past instant, **no**, because no snapshot was ever stored. |
| Depth limit | `depth=32` levels. On a 1–99¢ binary book that is effectively the full ladder. |

### 6.2 Permanently unavailable from historical data

- Any book state before the first snapshot we choose to persist. **Today that is: all of it.**
- Queue position, order IDs, cancel/replace, hidden size, aggressor side.
- Whether a specific displayed level was firm.
- Realised fills — dry-run produces none (`place_limit_order` returns `filled_count=0`, so
  `_record_fill` is unreachable and `trades` is empty **by construction**, not by accident).

**The only path to fill-realism without capital is a simulator over dense stored snapshots
plus prints. Everything needed to build that is available live and free; none of it is being
recorded.**

## 12. DISCOVERY EXPERIMENT

**Question:** *At the moment a bucket outcome becomes provable from the fastest feed we can
legally and freely obtain, is there displayed, sweepable size at a price that makes money after
fees — and does it survive adverse selection?*

**Design constraints met:** dry-run, no capital, timestamp-precise, captures `t1`, captures
Kalshi state around `t1`, measures L2 depth, measures repricing speed, estimates executable
fills, and separates displayed liquidity from realised fills (bounded, not proven).

### 12.1 Architecture

Add a **third ingest** and a **snapshot recorder**. Neither touches the trading path.

```
NEW  FiveMinutePoller        api.weather.gov/stations/{id}/observations?limit=20, every 60 s
       → running max on the 5-min series (SEPARATE from daily_tmax; never feeds trading)
       → on crossing detection  ⇒  emit lockin_event(t1_source='nws5min')

NEW  BookRecorder            for any ticker with an OPEN event, sample the L2 book on a
                             fixed schedule and on every event trigger

     MetarPoller (unchanged) → on crossing ⇒ emit lockin_event(t1_source='metar')  [= t2]
```

### 12.2 Trigger and sampling schedule

For each `(ticker, climate_date)`, arm a recorder when the 5-min running max is within
**3 °F** of any bucket boundary. Then record an L2 snapshot at:

```
baseline:      every 60 s while armed
event window:  t_detect − 10, −5, −2, −1 min                  (pre-detection)
               t_detect + 0 (immediately), +30 s, +1, +2, +5, +10, +15, +30, +60 min
               t2 − 1 min, t2 + 0, +1, +2, +5, +10, +30, +60 min   (t2 = METAR publication)
close-out:     one snapshot at market close
```

Both `t1` (5-min feed) and `t2` (METAR) events are recorded for **every** detection, including
the ones already at 100¢ — those are the control group and they are 56 % of the sample.

### 12.3 Record for every event

Non-negotiable fields (full schema in §13):

- **Weather:** `t1_obs_utc`, `t1_ingest_utc`, `t1_source`, running max before and after, the
  boundary crossed, **the crossing margin in °F**, the raw observation value and its precision,
  and the same triple for `t2`.
- **Market, at every snapshot:** full ask ladder and full bid ladder (price, size, per level),
  `best_bid`, `best_ask`, `spread`, `depth_total`, `vwap` for target sizes **{10, 25, 50, 100,
  250}**, `fillable_size`, `book_cleared`, plus the fetch's own `requested_at`/`received_at` so
  round-trip latency is recorded.
- **Outcome:** official settlement, **whether the detection was correct**, and settlement time.
- **Counterfactual P&L:** for each target size, `vwap`, fee at that vwap, net if correct, net if
  wrong.

### 12.4 Duration and power

At the observed rate (564 detections / 35 days ≈ **16/day**, of which ~28 % are claimed
discounted ≈ 4.5/day), **21 days yields ~340 detections and ~95 discounted windows** — enough
to put a ±5 ¢ confidence interval around a 17 ¢ mean and to test the adverse-selection
hypothesis at the margin bands. **Run it for 21 days minimum, 30 preferred.**

### 12.5 Cost

Storage: ~340 events × ~25 snapshots × ~64 levels ≈ 550 k rows ≈ 60 MB. Traffic: one extra
weather request per station per minute (7/min) and, while armed, a handful of orderbook GETs per
minute — well inside the existing 8 req/s token bucket. **Zero dollars.**

### 12.6 What it can and cannot settle

| Settles | Does not settle |
|---|---|
| Is there displayed size at a profitable price at `t1`? | Whether a quote was firm |
| How fast does the book reprice after `t2`? | Queue position |
| Is the discount concentrated in ambiguous (low-margin) detections? | Adverse selection *by informed counterparties* specifically |
| VWAP at realistic sizes, net of fees | Market impact of our own order |
| Which stations/hours carry the edge | Winter behaviour |

**The residual — "would it fill" — is only resolvable with real money.** But if this experiment
shows no displayed size at a profitable VWAP, the question never arises, and that is the point.

## 13. DATA SCHEMA

Three new tables. All timestamps are **ISO-8601 UTC strings with microseconds** (matching the
existing ledger's convention); all prices are **integer cents**; all temperatures are **REAL
°F**. Nothing here touches an existing table.

### 13.1 `lockin_events` — one row per (ticker, detection source)

```sql
CREATE TABLE lockin_events (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  ticker              TEXT    NOT NULL,          -- e.g. KXHIGHPHIL-26AUG03-T87
  series              TEXT    NOT NULL,          -- KXHIGHPHIL
  icao                TEXT    NOT NULL,          -- KPHL
  climate_date        TEXT    NOT NULL,          -- YYYY-MM-DD, fixed-LST climate day

  -- ---- detection ----------------------------------------------------------
  source              TEXT    NOT NULL,          -- 'nws5min' | 'metar' | 'onemin' | 'backfill'
  obs_utc             TEXT    NOT NULL,          -- observation VALID time that proved it
  ingest_utc          TEXT    NOT NULL,          -- when we received that observation
  detect_utc          TEXT    NOT NULL,          -- when the rule fired
  side                TEXT    NOT NULL,          -- 'yes' | 'no'
  strike_type         TEXT    NOT NULL,          -- greater | less | between
  floor_f             REAL,                      -- integer strike, NULL for tail-low
  cap_f               REAL,                      -- integer strike, NULL for tail-high
  boundary_f          REAL    NOT NULL,          -- the boundary actually crossed
  running_max_f       REAL    NOT NULL,          -- running max at detection
  prev_max_f          REAL,                      -- running max at the previous observation
  margin_f            REAL    NOT NULL,          -- running_max_f - boundary_f   ★ THE KEY FIELD
  obs_precision_f     REAL    NOT NULL,          -- 0.18 for tenths-C, 1.8 for whole-C
  ambiguous           INTEGER NOT NULL,          -- 1 if margin_f < 0.5 (rounding band)

  -- ---- cross-source linkage ----------------------------------------------
  paired_event_id     INTEGER,                   -- the 'metar' row for the same crossing
  lead_seconds        REAL,                      -- t2_obs - t1_obs, when paired

  -- ---- outcome (filled in at settlement) ---------------------------------
  settled_result      TEXT,                      -- 'yes' | 'no' | NULL until settled
  settled_at_utc      TEXT,
  call_correct        INTEGER,                   -- 1 / 0 / NULL   ★ grades EVERY detection
  cli_high_f          REAL,                      -- official CLI value, when obtainable

  UNIQUE (ticker, source, climate_date),
  FOREIGN KEY (paired_event_id) REFERENCES lockin_events(id)
);
CREATE INDEX ix_lockin_events_time   ON lockin_events(detect_utc);
CREATE INDEX ix_lockin_events_margin ON lockin_events(margin_f);
```

> `margin_f` and `call_correct` together are the two fields whose absence caused the two
> largest errors in this project. Every detection gets graded, tradeable or not.

### 13.2 `book_snapshots` — one row per (ticker, sample instant)

```sql
CREATE TABLE book_snapshots (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  ticker              TEXT    NOT NULL,
  event_id            INTEGER,                   -- NULL for baseline samples
  reason              TEXT    NOT NULL,          -- 'baseline'|'pre'|'t1'|'t2'|'offset'|'close'
  offset_seconds      REAL,                      -- signed, relative to the event; NULL if baseline

  requested_at_utc    TEXT    NOT NULL,          -- clock before the HTTP call
  received_at_utc     TEXT    NOT NULL,          -- clock after   ★ gives round-trip latency
  server_date_hdr     TEXT,                      -- Kalshi's Date header, if present
  rtt_ms              REAL    NOT NULL,

  best_yes_bid_cents  INTEGER,  best_yes_bid_size  INTEGER,
  best_yes_ask_cents  INTEGER,  best_yes_ask_size  INTEGER,
  best_no_ask_cents   INTEGER,  best_no_ask_size   INTEGER,
  spread_cents        INTEGER,                   -- best_yes_ask - best_yes_bid
  yes_depth_total     INTEGER  NOT NULL,         -- contracts across the whole YES ask ladder
  no_depth_total      INTEGER  NOT NULL,
  n_yes_levels        INTEGER  NOT NULL,
  n_no_levels         INTEGER  NOT NULL,
  market_status       TEXT,                      -- active | closed | settled
  volume_fp           REAL,                      -- lifetime, from /markets  (NOTE: _fp suffix)
  open_interest_fp    REAL,

  ladder_json         TEXT    NOT NULL,          -- {"yes_bids":[[p,s],…],"no_bids":[[p,s],…]}
                                                 -- raw Kalshi representation, both sides,
                                                 -- so any future derivation is possible
  UNIQUE (ticker, received_at_utc),
  FOREIGN KEY (event_id) REFERENCES lockin_events(id)
);
CREATE INDEX ix_book_snapshots_evt ON book_snapshots(event_id, offset_seconds);
```

> Store the **raw ladder**, not just derived metrics. Every derived quantity in this project
> that was stored without its inputs (`daily_tmax` in place, `prob` without its truncation
> bound) later had to be reconstructed by inversion. Do not repeat that.

### 13.3 `sweep_metrics` — one row per (snapshot, target size)

Denormalised deliberately: it makes the analysis a single `GROUP BY` and costs ~5× the rows of
`book_snapshots`, which is negligible.

```sql
CREATE TABLE sweep_metrics (
  snapshot_id         INTEGER NOT NULL,
  side                TEXT    NOT NULL,          -- 'yes' | 'no' (the side we would BUY)
  target_size         INTEGER NOT NULL,          -- 10 | 25 | 50 | 100 | 250
  fillable_size       INTEGER NOT NULL,          -- contracts obtainable ≤ ceiling
  book_cleared        INTEGER NOT NULL,          -- 1 if the ladder could not supply target
  top_ask_cents       INTEGER,
  vwap_cents          REAL,                      -- volume-weighted sweep price
  slippage_cents      REAL,                      -- vwap_cents - top_ask_cents   ★ the illusion
  ceiling_cents       INTEGER NOT NULL,          -- 98
  fee_cents           REAL    NOT NULL,          -- ceil(0.07 * N * P * (1-P)) at the VWAP
  net_if_correct_usd  REAL    NOT NULL,          -- (100 - vwap)*N/100 - fee
  net_if_wrong_usd    REAL    NOT NULL,          -- -vwap*N/100 - fee
  PRIMARY KEY (snapshot_id, side, target_size),
  FOREIGN KEY (snapshot_id) REFERENCES book_snapshots(id)
);
```

### 13.4 What each analysis becomes

| Analysis | Query shape |
|---|---|
| **edge size** | `net_if_correct_usd` at `reason='t1'`, grouped by `target_size` |
| **liquidity** | `yes_depth_total`, `fillable_size`, `book_cleared` rate |
| **slippage** | `slippage_cents` — directly measures the depth illusion |
| **latency** | `lead_seconds` (t1→t2), `ingest_utc − obs_utc`, `rtt_ms` |
| **fill probability** | `1 − book_cleared` at each size; upper bound only |
| **expected value** | `p·net_if_correct + (1−p)·net_if_wrong`, with `p` from `call_correct` |
| **P&L** | sum of the above over events |
| **capital efficiency** | `vwap × size` held from `detect_utc` to `settled_at_utc` |
| **market efficiency** | `top_ask_cents` as a function of `offset_seconds` — the decay curve |
| **station differences** | group by `icao` |
| **time-of-day** | `detect_utc` converted to LST via the station offset |
| **weather-variable** | join `margin_f`, `prev_max_f`, `obs_precision_f` — **and this is how P0-3 (adverse selection) gets answered: regress the discount on `margin_f`** |

## 14. DECISION FRAMEWORK

All thresholds assume the §12 dataset, 21+ days, and are stated per 100-contract clip.
**Gate 0 is unconditional and precedes every other branch.**

### GATE 0 — correctness (blocking, no exceptions)

> Do not proceed past this gate on any branch, including paper trading, until:
> **`call_correct = 1` for 100 % of detections that pass the deployed rule's entry test, over
> ≥ 300 detections.** Today it is ~96.8 %, and 9.5 % wrong in the sub-0.1 °F band.
> A "riskless arbitrage" with a 3 % error rate is not an arbitrage.

### A. KILL the strategy

Any **one** of:

1. **Depth:** median `fillable_size` at `reason='t1'` and `vwap ≤ 97¢` is **< 25 contracts**
   across the 21-day sample. *(The edge cannot be sized; opportunity cost of the engineering
   exceeds any return.)*
2. **Edge after slippage:** mean `net_if_correct_usd` at `target_size=100`, over **all**
   detections (including 100¢ ones), is **< $0.50/event**. At ~16 detections/day that is
   < $2,900/yr gross before any wrong call — below the maintenance cost of the system.
3. **Adverse selection:** the discount is concentrated in ambiguous detections — specifically,
   `corr(discount_cents, margin_f) < −0.3` **and** mean `call_correct` among discounted windows
   is **< 0.98**. *(The market is cheap because it is right and we are wrong.)*
4. **Decay:** median time from `t1` to `top_ask ≥ 98¢` is **< 120 s**. *(No feed we can build
   reaches it.)*
5. **Correctness cannot be fixed:** no margin threshold achieves 100 % `call_correct` while
   retaining ≥ 20 % of discounted detections.

### B. CONTINUE RESEARCH (stay in dry-run, keep instrumenting)

**All** of:

- Gate 0 not yet satisfied, **or** sample < 300 detections / < 21 days; **and**
- none of the kill criteria met; **and**
- mean `net_if_correct_usd` at size 100 is in **$0.50 – $3.00/event**; **or**
- discounted-window count is **< 40** (too thin for a mean).

### C. BEGIN PAPER TRADING (simulated fills against recorded books)

**All** of:

1. Gate 0 satisfied: **100 % `call_correct` over ≥ 300 detections** under the deployed rule.
2. ≥ **21 days** and ≥ **300** detections recorded with full L2.
3. Median `fillable_size` at `vwap ≤ 97¢` **≥ 50 contracts**.
4. Mean `net_if_correct_usd` at size 100 **≥ $3.00/event**, and **≥ $1.00** at the 25th
   percentile.
5. `corr(discount_cents, margin_f) > −0.15` — the discount is **not** explained by ambiguity.
6. Median `t1 → 98¢` decay **≥ 600 s** (10 min of usable window against a ~200 s pipeline).
7. Sub-hourly coverage at **≥ 5** of 7 stations, with measured publication lag **≤ 20 min**.

### D. BEGIN TINY LIVE TRADING

**All of C**, plus:

1. **≥ 30 consecutive days** of paper results, with realised-vs-simulated VWAP deviation
   **≤ 2¢** — i.e. the simulator is calibrated.
2. Projected net **≥ $500/month** at 100 contracts after fees, using the *5th percentile* of
   the bootstrapped event distribution, not the mean.
3. Position limits hard-set: **`WA_MAX_FRACTION_PER_MARKET ≤ 0.01`** (1 %, not the current 5 %)
   and a **daily loss stop at 2 %** of equity. Rationale: a single wrong lock-in at 98¢ is a
   near-total loss of the clip, and Kelly is a **no-op for Strategy 1** (`risk_manager.py:186`),
   so `max_fraction_per_market` is the *only* binding control.
4. `WA_ALLOW_LIVE_MODEL_EDGE=false` verified in the running process, and the startup
   `LIVE TRADING ENABLED` warning confirmed in the log.
5. Initial capital **≤ $1,000**, size **≤ 10 contracts/event** — enough to measure fills, small
   enough that Gate-0 being subtly wrong costs ≤ $10/event.
6. A kill switch that does not require an SSH session.

### E. SCALE

**All of D**, plus, over **≥ 60 days live**:

1. Realised net **≥ $300/month** at 10-contract size (i.e. ≥ $3,000/mo pro-rata at 100).
2. **Zero** wrong lock-ins in ≥ 200 live detections.
3. Realised fill rate **≥ 80 %** of `fillable_size` at the modelled VWAP ± 2¢.
4. Sharpe of daily P&L **≥ 1.5** over ≥ 60 trading days.
5. Scale by **≤ 2× per 30 days**, and stop at the size where realised slippage exceeds modelled
   slippage by > 3¢ — that is the market-impact ceiling.

**Three honest caveats:**
1. **1 °C quantization (1.8 °F).** The 5-min rows carry whole °C. Bucket boundaries are 1 °F

   ±0.08 °F METAR error that already produces a 9.5 % false-positive rate in the ambiguous
   band.** Any rule fed by this feed **must** carry a margin requirement (§16 DO NOW #1).

2. **KNYC and KDEN have no 5-minute product.** That is 132 of 564 detections (23 %), and Denver
   alone is 98 — the station with the largest diurnal range and therefore the most crossings.
3. Publication lag was measured once, at one instant. **It needs a proper campaign** (sample the
   newest-observation age every minute for a week).

### BIGGEST CURRENT RISK

> **The single assumption most likely to sink this: that the ~17¢ discount observed at `t1`
> represents free money rather than the market correctly pricing a genuinely uncertain
> outcome — an outcome our detection rule calls "certain" only because it compares a float to
> an integer.**

This is not speculative. It is the intersection of three independently established facts:

- the lock-in rule is **wrong 9.5 % of the time** when the margin is under 0.1 °F (§3.5, measured);
- **169 of 564 detections (30 %)** sit in exactly that sub-0.1 °F band (§3.5, measured);
- **56 % of lead windows are at 100¢ and 28 % are discounted** (claimed) — and *nothing has
  ever tested whether the discounted 28 % and the ambiguous 30 % are the same events.*

If they overlap, the "edge" is a bet that a market which correctly recognises a coin-flip is
mispricing it, taken at up to 98¢ with a 2 %-of-notional upside and a 98 % downside. The
payoff asymmetry is brutal: at 98¢ you need to be right **50 : 1** to break even. A 3 % error
rate turns a "riskless arbitrage" into a **−$0.94 per contract** expectation.

The second-largest risk is procedural and is visible throughout this audit: **four load-bearing
numbers in the project's own documentation did not survive re-derivation, and three of them
were filed under "SOLID — mechanically verified".** The pattern is consistent — favourable
results were recorded as prose without a committed, re-runnable artefact. `HANDOFF.md`'s own
author's note anticipates this exactly ("when a result looks good, assume the measurement is
broken until proven otherwise"). **Applied to itself, that heuristic would have caught all
four.** Any figure in this project that lacks a script capable of regenerating it should be
treated as a hypothesis.
